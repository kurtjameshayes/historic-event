FUNCTIONAL DESIGNHistorical Causal Timeline AgentAn Agentic AI System for Causal Historical AnalysisVersion 1.0March 2026
1. Project Overview1.1 PurposeThe Historical Causal Timeline Agent is an agentic AI system that accepts a natural language question about a historical event and autonomously produces a multi-threaded causal timeline showing how preceding events, conditions, and decisions converged to precipitate the event in question.Unlike a simple LLM prompt-and-response, this system uses an iterative research loop: it plans a research agenda, executes searches, evaluates gaps and contradictions in its findings, adapts its plan, and repeats until it achieves sufficient causal coverage. The output is a directed acyclic graph (DAG) of causally linked events rendered as an interactive timeline.1.2 Value Proposition� Demonstrates a full Plan ? Act ? Observe ? Adapt agentic loop with visible reasoning traces� Produces structured causal analysis, not just a flat list of dates� Self-critiques and iterates, filling gaps and resolving contradictions autonomously� Provides sourced, confidence-scored causal claims that users can verify1.3 ScopeIn scope: Historical events with documented public records (wars, revolutions, political shifts, economic crises, technological breakthroughs, social movements). Events from antiquity through the modern era.Out of scope: Speculative future events, ongoing/current events with incomplete records, classified or restricted information, conspiracy theories or fringe historical revisionism.1.4 Key TerminologyTermDefinitionCausal ThreadA line of causally connected events leading toward the target eventTarget EventThe historical event the user is asking aboutCausal DAGDirected acyclic graph where nodes are events and edges represent causal influenceConfidence ScoreA 0.0�1.0 rating of how well-supported a causal link is by the evidence foundResearch CycleOne full iteration of the Plan ? Act ? Observe ? Adapt loopCoverage ThresholdMinimum criteria for the agent to consider its research sufficientCausal DepthHow many levels of predecessor events to trace back from the target event2. User Experience2.1 User Flow1. User enters a natural language question (e.g., "What caused the Fall of the Berlin Wall?").2. System displays a status panel showing the agent�s research in progress: current phase, threads being investigated, sources found, cycle count.3. Upon completion, system presents an interactive causal timeline with the DAG visualization, a narrative summary, and source citations.4. User can drill into any node to see supporting evidence, click causal edges to see the reasoning, or request the agent to investigate a thread more deeply.2.2 Input SpecificationFieldTypeRequiredDescriptionquerystringYesNatural language question about a historical eventmax_depthintegerNo (default: 3)How many causal levels deep to trace (1�5)max_cyclesintegerNo (default: 5)Maximum research cycles before forced completionfocus_threadsstring[]NoUser-specified causal threads to prioritize2.3 Output SpecificationThe system produces three output artifacts:� Causal DAG: A directed acyclic graph of events with causal edges, confidence scores, and source citations. Serialized as JSON for programmatic access.� Interactive Timeline: A visual rendering of the DAG as a horizontal timeline with branching causal threads. Events are positioned chronologically on the x-axis, with parallel threads stacked vertically.� Narrative Summary: A prose explanation of the causal chain, generated from the DAG, suitable for reading as a standalone document.2.4 Status Panel (Real-Time Feedback)While the agent works, the user sees a live status panel showing:� Current phase (Planning / Researching / Evaluating / Critiquing / Finalizing)� Active causal threads and their status (investigating / gap detected / complete)� Source count and research cycle number� A scrollable log of the agent�s reasoning trace (what it planned, what it found, what gaps it identified, how it adapted)3. System Architecture3.1 High-Level ArchitectureThe system is composed of five core components that interact through a central orchestrator:ComponentResponsibilityOrchestratorControls the agentic loop. Manages state transitions between Plan, Act, Observe, and Adapt phases. Enforces cycle limits and coverage thresholds.Planner AgentDecomposes the user query into an initial set of causal threads. Generates and refines the research agenda. Decides thread priority and depth.Research AgentExecutes searches per thread. Extracts dated events and causal claims from sources. Structures findings as candidate nodes and edges for the DAG.Critic AgentEvaluates the current DAG for gaps, contradictions, weak links, missing counter-narratives, and source quality. Produces a structured critique.RendererTransforms the final DAG into the interactive timeline visualization and narrative summary.3.2 Tech StackLayerTechnologyRationaleBackendPython / FlaskFamiliar stack, fast iterationDatabaseMongoDBFlexible schema for heterogeneous event data; native graph-like queries with $graphLookupLLM ProviderAnthropic Claude APIStrong reasoning, structured output, large context windowSearchWeb search API + Wikipedia APIBroad coverage for historical eventsVector StoreMongoDB Atlas Vector Search (optional)Semantic retrieval over cached research resultsFrontendReact + D3.js or vis.jsInteractive DAG visualization with zoom/pan/drill-downReal-TimeServer-Sent Events (SSE)Stream agent status updates to the frontend status panel3.3 Data FlowThe following sequence describes one complete research cycle:1. User submits query via the frontend. Flask endpoint receives the request and creates a new session document in MongoDB.2. Orchestrator invokes the Planner Agent with the user query. The Planner returns a structured research agenda: a list of causal threads, each with a description and priority score.3. Orchestrator iterates through threads by priority. For each thread, the Research Agent executes web searches, extracts dated events and causal claims, and structures them as candidate DAG nodes and edges.4. Research results are written to MongoDB. The Orchestrator assembles the current DAG from all results.5. Orchestrator invokes the Critic Agent with the current DAG. The Critic returns a structured evaluation: gaps, contradictions, weak links, new threads to explore.6. Orchestrator evaluates the critique against the coverage threshold. If coverage is sufficient or max_cycles is reached, proceed to rendering. Otherwise, update the research agenda with the Critic�s recommendations and loop back to step 3.7. Renderer generates the interactive timeline and narrative summary from the final DAG. Results are returned to the frontend.4. Agent Design4.1 Planner Agent4.1.1 InputThe user�s natural language query and (on subsequent cycles) the Critic�s feedback from the previous cycle.4.1.2 ProcessingThe Planner makes a single LLM call with a structured prompt that instructs it to:� Identify the target event and its approximate date� Decompose the question into 3�6 distinct causal threads (e.g., political, economic, social, military, ideological, technological)� For each thread, provide a description, a priority score (1�5), and initial search queries� On subsequent cycles, incorporate the Critic�s feedback: add new threads, reprioritize existing ones, refine search queries for thin areas4.1.3 Output SchemaFieldTypeDescriptiontarget_eventobject{ name, approximate_date, description }causal_threadsarrayEach: { id, name, description, priority, search_queries[], status }research_notesstringFree-text reasoning about the decomposition strategy4.2 Research Agent4.2.1 InputA single causal thread with its search queries.4.2.2 ProcessingFor each search query in the thread:1. Execute web search. Retrieve top 5�10 results.2. For each result, fetch the page content and pass it to the LLM with an extraction prompt.3. The extraction prompt instructs the LLM to identify: dated events relevant to the causal thread, causal claims ("Event A led to Event B because..."), source quality assessment (primary source, secondary, opinion, etc.).4. Deduplicate events by fuzzy matching on date + description. Merge causal claims from multiple sources.5. Assign initial confidence scores based on source count, source quality, and inter-source agreement.4.2.3 Output SchemaFieldTypeDescriptionthread_idstringID of the causal thread this research belongs toeventsarrayEach: { id, date, title, description, sources[], thread_id }causal_edgesarrayEach: { from_event_id, to_event_id, reasoning, confidence, sources[] }raw_sourcesarrayEach: { url, title, quality_rating, relevant_excerpts[] }4.3 Critic Agent4.3.1 InputThe full current DAG (all events, edges, and their metadata) plus the original user query.4.3.2 ProcessingThe Critic performs a structured evaluation by answering these questions:1. Temporal gaps: Are there significant time periods within any thread that have no events? (e.g., a thread jumps from 1953 to 1989 with nothing in between)2. Causal gaps: Are there events that appear to be effects without identified causes, or causes without documented effects?3. Weak links: Are any causal edges supported by only a single low-quality source?4. Missing threads: Given the target event, are there obvious causal dimensions that are entirely unrepresented?5. Contradictions: Do any sources disagree on whether a causal relationship exists or on the direction of causality?6. Proportionality: Is research evenly distributed, or are some threads over-researched while others are thin?7. Counter-narratives: Are there well-known alternative explanations for the target event that are not represented?4.3.3 Output SchemaFieldTypeDescriptionoverall_scorefloat0.0�1.0 composite coverage scoreis_sufficientbooleanTrue if overall_score >= coverage threshold (default 0.7)temporal_gapsarrayEach: { thread_id, start_date, end_date, severity }causal_gapsarrayEach: { event_id, gap_type, description }weak_linksarrayEach: { edge_id, current_confidence, reason }missing_threadsarrayEach: { suggested_name, rationale, search_queries[] }contradictionsarrayEach: { event_ids[], description, resolution_suggestion }recommendationsarrayPrioritized list of actions for the next research cycle4.4 Orchestrator LogicThe Orchestrator is the control loop, implemented in Python (not LLM-driven). It manages state transitions:PhaseActionTransition ConditionPLANInvoke Planner AgentAlways ? RESEARCHRESEARCHInvoke Research Agent for each threadAll threads processed ? EVALUATEEVALUATEAssemble DAG, invoke Critic AgentCritic says sufficient ? RENDER, else ? ADAPTADAPTUpdate agenda per Critic feedbackMax cycles reached ? RENDER, else ? RESEARCHRENDERInvoke RendererAlways ? COMPLETE5. Data Model (MongoDB)5.1 Collections5.1.1 sessionsOne document per user query. LLM Prompt DesignEach agent uses a dedicated system prompt with structured output requirements. All prompts enforce JSON output for machine-parseable responses.7.1 Planner Prompt Strategy� System role: You are a historical analyst. Your job is to decompose a question about a historical event into distinct causal threads.� Output: JSON matching the Planner output schema (Section 4.1.3).� Key instruction: Prioritize threads by causal proximity and historical significance. Prefer threads that represent different dimensions (political, economic, social, etc.) to avoid redundancy.� On subsequent cycles: Include the Critic�s feedback as context. Instruct the Planner to add, remove, or reprioritize threads accordingly.7.2 Research Extraction Prompt Strategy� System role: You are a historical research assistant. Extract dated events and causal claims from the provided source text.� Input: Source text (web page content) + the causal thread description for context.� Output: JSON array of events and causal edges.� Key instruction: Only extract claims that are explicitly stated or strongly implied by the source. Do not infer causation beyond what the source supports. Rate source quality (primary, secondary, tertiary, opinion).7.3 Critic Prompt Strategy� System role: You are a critical historical reviewer. Evaluate this causal timeline for completeness, accuracy, and balance.� Input: The full DAG serialized as JSON + the original user question.� Output: JSON matching the Critic output schema (Section 4.3.3).� Key instruction: Be specific in identifying gaps. For each gap, suggest concrete search queries that could fill it. Flag any well-known counter-narratives or alternative explanations that are missing.8. Confidence Scoring ModelEvery causal edge receives a composite confidence score calculated from four factors:FactorWeightDescriptionSource Count0.25More independent sources supporting the claim = higher score. 1 source = 0.3, 2 = 0.6, 3+ = 1.0Source Quality0.30Average quality rating of supporting sources. Primary/academic = 1.0, secondary/reputable media = 0.7, tertiary/general = 0.4, opinion = 0.2Inter-Source Agreement0.25Degree to which sources agree on the causal claim. Full agreement = 1.0, partial = 0.5, contradiction = 0.1LLM Extraction Confidence0.20The LLM�s self-assessed confidence that it correctly extracted the causal claim from the sourceComposite score = (0.25 ? source_count_score) + (0.30 ? quality_score) + (0.25 ? agreement_score) + (0.20 ? extraction_confidence)Edges with composite scores below 0.3 are flagged as weak links and prioritized for additional research in the next cycle.9. Coverage Threshold ModelThe Critic�s overall_score is calculated from:� Thread coverage: Proportion of identified causal threads with at least 3 events and 2 causal edges (weight: 0.30)� Temporal coverage: Proportion of the timeline with no gaps exceeding 20% of the total timespan (weight: 0.25)� Edge confidence: Mean confidence score across all causal edges (weight: 0.25)� Balance: Inverse of the coefficient of variation of events per thread, i.e. more evenly distributed research scores higher (weight: 0.20)Default threshold for sufficiency: 0.70. The agent continues iterating until this is met or max_cycles is reached.10. Frontend Visualization10.1 Timeline View� Horizontal axis: chronological time. Error Handling and ResilienceFailure ModeHandling StrategyUser ImpactLLM API timeout/errorRetry with exponential backoff (3 attempts). If all fail, skip current thread and continue.Thread marked as incomplete; user notified via SSE.Web search returns no resultsResearch Agent tries alternative query formulations (up to 3). If all fail, mark thread as thin.Critic detects thin thread and may deprioritize it.LLM returns malformed JSONAttempt JSON repair (strip markdown fences, fix trailing commas). If repair fails, retry with stricter prompt.No user impact unless all retries fail.MongoDB write failureRetry once. If persistent, log error and continue with in-memory state.Session may not be recoverable if server restarts.Cycle limit reached with low scoreProceed to render with available data. Include coverage score and gap summary in output.User sees partial timeline with explicit quality indicators.12. Future Enhancements� Vector search over cached research: Embed past research results in MongoDB Atlas Vector Search. Before executing a new search, check if relevant information already exists in the cache. Reduces API calls and speeds up repeat queries on similar topics.� User-guided exploration: Allow users to add events or causal links manually, injecting them into the DAG. The Critic then evaluates whether the user�s additions are supported by evidence.� Comparative timelines: Support queries like "Compare the causes of WWI and WWII" by running parallel agent sessions and generating a comparative visualization.� Source document ingestion: Allow users to upload PDFs or articles as primary sources. The Research Agent incorporates these alongside web search results.� Multi-language support: Research in multiple languages for events where English-language sources are insufficient (e.g., researching the Meiji Restoration with Japanese sources).� Fine-tuned extraction model: Train a specialized model on historical event extraction to improve accuracy over general-purpose LLMs for the Research Agent�s extraction task.Historical Causal Timeline Agent � Functional DesignPage 2
